# @status/backend

NestJS API in TypeScript (Express adapter). Serves the app's data from Supabase Postgres; will run the AI agents.

## Commands

From this directory: `pnpm dev` (watch mode), `pnpm build`, `pnpm start` (runs `dist/`), `pnpm lint` (oxlint), `pnpm typecheck`.
From the repo root: `pnpm --filter @status/backend <script>`, or `pnpm dev:backend`.

Database:

- `pnpm db:start` / `pnpm db:stop` — local Supabase stack in Docker (needs Docker Desktop running). Studio UI at http://127.0.0.1:55323.
- `pnpm db:generate --name <change>` — after editing `src/db/schema.ts`, generate a SQL migration into `supabase/migrations/`. For SQL drizzle can't express (extensions, functions), `pnpm exec drizzle-kit generate --custom --name <change>` creates an empty migration to fill in.
- `pnpm db:reset` — recreate the local DB from all migrations (deletes local data)
- `pnpm db:seed` — wipe all worlds and insert one demo world (refuses non-local DBs unless `SEED_ALLOW_REMOTE=1`)
- Cloud (project ref `rvudxcehbndngcoagasc`, Frankfurt `eu-central-1`; pick a region near Israel, since every query is a round trip): with the Transaction pooler string (port 6543) in `.env` as `DATABASE_URL` (the Session pooler, port 5432, caps all clients at 15 connections, and the backend alone opens up to 10), apply migrations with `pnpm exec supabase db push --db-url` and the same string on port 5432

First-time local setup: `cp .env.example .env`, `pnpm db:start`, `pnpm db:seed`, `pnpm dev`.

AI: `pnpm ai:try` builds and runs `src/ai/try.ts`, one `generate()` and one of each `decide()` question type against the configured providers.

News: `pnpm news:generate` draws the photos for Pull, the app's made-up news site (articles in `src/news/articles.ts`: category, headline, subheadline, lead, an English photo prompt), through Cloudflare Workers AI with one shared news-photo style (`NEWS_PHOTO_STYLE`), crops each to 16:9 (1200×675) and compresses it with `sharp`, and writes them with `articles.json` into `services/frontend/public/news/`. Existing photos are kept (`--force` redraws all), so adding an article draws only its own. A dev script: it calls the image provider directly, not through `AiService`, and needs no database.

## Structure

- `src/main.ts` — bootstrap; sets the global `/api` prefix and CORS
- `src/app.module.ts` — root module; register feature modules in `imports`
- `src/<feature>/` — one folder per feature: `<feature>.module.ts`, `<feature>.controller.ts`, `<feature>.service.ts`
- `src/db/schema.ts` — Drizzle schema, the source of truth for the database. `client.ts` creates the connection; `db.module.ts` provides it globally (`@Inject(DB) db: Db`); `seed.ts` is the dev seed.
  - Social: `worlds` (also holds tick count, energy and the tick lock), `accounts` (the human + agents), `posts`, `comments`, `stories`, `conversations`, `messages`
  - Agents and story: `characters` (persona + secrets, 1:1 with an agent account), `character_memories` (text + `vector(1024)` embedding, HNSW cosine index; null until embedded), `relationships` (directed score -100..100 from a character to another character or the player), `story_beats` (ordered plot points, `pending`/`active`/`done`, with per-character `directions`), `story_flags` (per-world JSON key/value)
- `src/ai/` — `AiService` (global via `AiModule`): `generate(prompt, { system })` for Hebrew text and `decide(state, question)` for typed decisions. Questions mirror Jev's primitives: `choice` (returns one of its option keys), `score` (0..1 across ordered levels), `yesNo` (probability of yes). Providers are in `src/ai/providers/`, selected by `AI_TEXT_PROVIDER` (ollama | anthropic) and `AI_DECISION_PROVIDER` (ollama | anthropic | jev). `generateImage(prompt)` returns a JPEG from `AI_IMAGE_PROVIDER` (none | cloudflare: Workers AI FLUX.1 schnell), or null for none. Pass `hebrew: false` to `generate()` for text users never see, like English image prompts.
- `src/accounts/` — `GET /api/me`, `PATCH /api/me` `{ gender }` (the welcome screen; only while the gender is unset, else 409 `GENDER_ALREADY_SET`: changing it mid-story would leave everything written so far in the other gender), plus `CurrentUserService` (who is making the request) and `toUser` (DB row → API `User`)
- `src/storage/` — `StorageService` (global): uploads to the public Supabase Storage bucket `media` (created on startup) under `<worldId>/<kind>/<uuid>.<ext>`, returns the public URL. Needs `SUPABASE_URL` and `SUPABASE_SECRET_KEY`; without them uploads fail and the rest works.
- `src/feed/` — `GET /api/feed` (posts with comments), `GET /api/me/posts` (the user's own posts), `GET /api/accounts` (everyone else in the world, the agents), `GET /api/accounts/:username` (a `Profile`: user, public `accounts.bio`, their posts; 404 for unknown), `POST /api/posts` (multipart `image` + `caption`; without `image` it's a text-only post, `image_url` null, and the caption is required. With a photo: it's uploaded, then described in the background by `generate()` with the image attached, into `posts.image_description`), `GET /api/stories` (grouped by author; only the last 24 hours, `STORY_TTL_MS`), `POST /api/posts/:id/comments` (the user comments), `PUT /api/posts/:id/like` `{ liked }` (each world has one human, so the like is a `posts.player_liked` flag added on top of the displayed `like_count`)
- `src/conversations/` — `GET /api/conversations`, `POST /api/conversations` `{ username }` (opens the DM thread with an agent, created if needed, e.g. from their profile; free, only sending costs), `GET /api/conversations/:id`, `POST /api/conversations/:id/messages` (the user sends a DM; one energy point buys `DM_MESSAGES_PER_ENERGY` messages, counted down in `worlds.dm_credits`; 409 `NO_ENERGY`), `PUT /api/conversations/:id/read` (the user opened it: sets `conversations.player_read_at`; a conversation is `unread` when the agent wrote last, after that), `POST /api/stories/:id/reply` `{ text }` (`StoryRepliesController`: the user replies to an agent's story; a DM in their thread, created if needed, with `messages.story_id` set, so the chat shows the story and the agent's prompt says which story it is (`dmText`)), `POST /api/conversations/:id/reply` (the agent answers the last DM right away, via `AgentService.replyInDm`; `{ message: null }` if there's nothing to answer or a reply is already being written)
- `src/world/` — the simulation. `GET /api/world` (tick count + energy), `POST /api/world/tick` (advance one step; 409 `NO_ENERGY` / `TICK_IN_PROGRESS`).
  - `world.service.ts` — runs a tick: takes a per-world lock (`worlds.ticking_since`), then (1) every character plans in parallel, (2) the turns that run are picked: replies the player is waiting for (an unanswered DM, or a player comment on the character's own post) always run and don't count toward `TICK_MAX_ACTIONS`, then directed characters, then spontaneous ones in random order, (3) they're all written in parallel (`AgentService.compose`, AI only, saves nothing), (4) saved (`AgentService.commit`). It spends 1 energy and responds; the story advances (`StoryService.advance`) right after, still holding the lock. Each character acts at most once per tick. Energy is only spent if the tick succeeds; if every turn fails (AI provider down), it returns 503.
  - Prepared ticks: steps 1–3 are the slow part (~7 s of AI calls), so they run ahead of time (`prepare`), after each tick and whenever the world changes, and a tick usually only commits (~1.5 s). Between ticks only the player and background work change the world (agents act only in ticks), so a prepared tick is used only if a `fingerprint` (tick number, newest post/comment/DM, conversation count, active beat and who played it, flags, player gender) still matches; otherwise it's composed live (~8 s). `WorldChanges` (`world-changes.ts`) is how other services report changes: `changed()` after the player comments, posts or DMs, and `track()` around background work (photo uploads, the instant DM reply, photo descriptions, the story director) so preparing waits until it's done. Preparing is debounced (`PREPARE_DEBOUNCE_MS`), skipped without energy, and a prepared tick expires after `PREPARED_MAX_AGE_MS`. A missed notification only costs speed, never correctness. Ticks log where their time went (`Tick N took ...ms (prepared|live): ...`).
  - `agent.service.ts` — `compose()` writes a turn's text (a `Draft`) and `commit()` saves it; keep AI calls in compose and DB writes in commit, since composing can happen minutes before the tick it's used in. `plan()` builds the decision state (persona, secrets, memories, relationships, active beat, flags, recent feed, DMs with the player) and `decide()`s post (the option says how many posts others made since the character's last one: time between ticks depends on the player's energy, so posting follows feed activity, not hours) / text_post (no photo, `TEXT_POST_TASK`; saved right away, so others can react from the next tick) / story (a photo with a few words on it, `STORY_TASK`) / comment / comment_on_player_post (offered while the player has a post this character hasn't commented on; it also adds a like) / message_player / nothing (no message_player when the last DM is already theirs: no double-texting); `compose()` `generate()`s the text, and `commit()` saves it plus a memory.
  - `story.service.ts` — the storyline (a comedy: the director's system prompt sets an Israeli everyday-humor tone, and characters get a matching line in theirs). A beat (`story_beats`) has `directions`: what each involved character does (one concrete post, comment or DM to the player), by username. Directed characters get only their own direction in their prompt and decision state (never the beat description, which can hold others' secrets); they act before other spontaneous turns and are then added to `acted_by`. A beat is done when every directed character has acted, or after `BEAT_MAX_TICKS`. Then the next seeded (`pending`) beat starts, or, when none are left, the story director writes one in the background (`writeNextBeat`, ~10 s; ticks meanwhile run without a beat). The director is an AI writer that sees the whole cast (personas, secrets, relationships), the story so far (`worlds.story_summary`, which it also updates), recent beats, posts and the player's DMs, and returns JSON. Agents can't DM each other, so the player is everyone's confidant.
  - `arc.ts` — the season (`ARC`): a roommates sitcom in five acts ("30 יום לפלורנטין": the player is the new roommate in a Florentin flat, and the landlord is selling it in 30 days), with a player-facing `logline`, a premise, a director-only `truth` (everyone's secrets and how it can be solved) and per-act goals with `minBeats`/`maxBeats`. Written for the seed cast. Act 1 is scripted in the seed (three beats with planned scenes and the first choice); `FIRST_DIRECTED_ACT` is where the director takes over. `worlds.arc_act` / `arc_act_beats` track where a world is; the director gets the current act in its prompt (`arcSection`), says when a beat completes it (`actDone`, honored from `minBeats`, forced at `maxBeats`), and after the last act continues on its own (`AFTER_ARC`).
  - The story card (`GET /api/story` → `StoryNow`, `StoryService.storyNow`, `StoryController`): what the player sees of the story, player-safe only. Each beat has a `title` (the chapter name, never a secret), a `brief` (what's going on, in plain words) and a `hint` + `hintUser` (what to do now, whom to write to), written by the director or the seed. A seeded beat can carry `planned_scene`, inserted as a real scene when it starts (`next`). A beat lasts at least `BEAT_MIN_TICKS` (2), so the player gets a turn to read and answer it, and at most `BEAT_MAX_TICKS`.
  - Scenes ("מה קרה במציאות", table `scenes`, `ScenesController`: `GET /api/scenes`, `POST /api/scenes/:id/choose` `{ choice }`): what happens off the network, narrated to the player in the second person (they're there). The director may write one with a beat (required on the first and last beat of an act, with one retry); it can end with 2–3 `choices`. A photo is drawn from the scene's `image` prompt when an image provider is set. Choosing is free and once per scene (409 `ALREADY_CHOSEN`); if the scene's beat is still active, the choice ends it and the director writes the next beat from the choice right away. Characters see recent scenes as `recap` (third person, only what everyone there saw) plus the player's pick (`TickContext.realLife`, `toRealLife`), in both their decision state and system prompt. `TickResult.storyMoving` and `WorldStatus.storyWriting` let the feed wait for the next scene. Writing a beat retries twice on failure (`writeWithRetries`).
  - `energy.ts` — pure regeneration math (`ENERGY_MAX`, `ENERGY_REGEN_MINUTES`); energy is stored lazily as value + timestamp on `worlds`.
- `src/stats/` — the player's stats (`player_stats`, one row per world, 0..100, start at 50): aura, humor and drama. `GET /api/me/stats` → `PlayerStats`. Every player action (photo/text post, comment, DM, story reply, like/unlike) calls `StatsService.record`, which scores it with `score.ts`: pure heuristics, no AI calls (base points per action, laughs and emoji, drama words and `?!`, rambling, apologies, double-texting, a little noise so every action moves something) and saves the change with its Hebrew `reason`. It never throws.
- `src/common/` — `ZodBodyPipe` (request body validation) and shared zod schemas
- `src/health/` — `GET /api/health` liveness check
- `supabase/` — Supabase CLI project: `config.toml` (local stack) and `migrations/` (generated by drizzle-kit; don't edit by hand)

## Conventions

- Config comes from environment variables via `@nestjs/config` (`ConfigService`), loaded from `services/backend/.env`. Document every new variable in `.env.example`; never commit `.env` or API keys.
- Keep calls to external APIs and AI providers inside services, never in controllers.
- All AI calls go through `AiService`, never a provider directly. `generate()` prepends `HEBREW_RULE` to the system prompt. Keep decision questions and option keys in English (they're code), and Hebrew in what the user sees.
- Generation prompts (system prompt, task instructions, `HEBREW_RULE`) are written in Hebrew, using the infinitive ("לכתוב") so they fit any gender; English instructions made the output read like a translation. Decision questions stay in English.
- Gender: `accounts.gender` (female | male | null). Prompts tell each character to write about themselves in their own gender (`selfGender`) and how to address others (`addressAs`); null (a player who hasn't passed the welcome screen yet) means address them neutrally, e.g. in the plural. Never put slashed forms ("את/ה") in seed data or prompts: models copy them.
- `accounts.bio` is the public profile text anyone can read (the seed sets one per agent). Never put secrets there; those belong in `characters.secrets`.
- Personas, secrets, memories and beat descriptions are stored in Hebrew. Personas are written as instructions to the character in the second person ("את מאיה...").
- The Jev provider was written from the docs and hasn't been run (no API key yet); verify it, especially the `score` range, before relying on it.
- `EMBEDDING_DIMENSIONS` (1024) must match the embedding model; changing it requires a migration.
- Agents act during ticks, with one exception: a DM reply, which the frontend requests right after the user sends a message. User comments are saved immediately and answered on the next tick (as are DMs whose instant reply failed).
- Agent post photos: the character writes an English image prompt from its caption (`PHOTO_TASK`; people from behind or only hands, since faces aren't consistent yet), the image provider draws it (one retry), and it's uploaded to Storage. The prompt is saved as `image_description`, so other agents know what's in the photo. This runs in the background after the caption is written (`publish`), so a tick doesn't wait for it: the tick event carries the post's pre-generated ID, and the row is inserted only once the photo is ready (a few seconds later; other agents see it from the next tick). If generation fails twice the post is dropped rather than shown with an unrelated photo. With `AI_IMAGE_PROVIDER=none`, posts get a random picsum photo instead. Stories work the same way (`story`/`publishStory`, text in `stories.text`, the photo kept centered since the viewer crops it to 9:16). At most `MAX_MEDIA_PER_TICK` (2) posts and stories per tick, leaving room for comments; directed ones are exempt. Seed posts and stories still use picsum. Memories are saved without embeddings.
- Agents never see raw images: the user's photos are described once at upload (`posts.image_description`), and prompts and decision state include that text (`postContext`, `photo` in the feed state). `generate()` accepts `images` (base64) for this; both the Anthropic and Ollama (vision models like gemma4) providers support it.
- When testing with curl on Windows, send Hebrew bodies from a UTF-8 file (`--data-binary @body.json`); inline Hebrew arguments arrive as `????`.
- **Scope every query to the current user's world** (`worldId`). Worlds are private; one user must never see another world's rows.
- Every table enables RLS with no policies (`.enableRLS()` in the schema), which keeps Supabase's public REST API closed. The backend connects as `postgres` and bypasses RLS. Keep this on for new tables.
- Responses use the types from `@status/shared` (`import type`). Convert `Date` to ISO strings when mapping rows.
- `CurrentUserService` is a stand-in until Supabase Auth: it returns the oldest human account, cached for 60 s (each DB round trip to the cloud project costs ~300 ms).
- Local Supabase ports are 553xx, not the default 543xx, because Windows reserves 54240–54339 on this machine.
- `experimentalDecorators` and `emitDecoratorMetadata` must stay on in `tsconfig.json`; Nest's dependency injection relies on them.
- Output is CommonJS (no `"type": "module"`), which is what the Nest CLI expects.
